Pour supporter Media multi-images et Order (images + labels, correction manuelle)

interface IQuestion {
  type: 'Text' | 'Media' | 'Order'
  file: string          // 1 image
  files: string[]       // grille
  // NOUVEAU ↓
  orderItems: [{
    _id: string
    label: string
    file: string
  }]
  answer: string        // JSON pour Order
}

A — Additif (Recommandé) ⭐

On ajoute orderItems[] à l'interface existante. files[] est déjà dans le schéma Mongoose, juste absent de l'interface. Migration minimale, pas de refacto du store ni des events socket.

Pros

  • Aucune migration DB
  • Store/sockets inchangés
  • Livrable rapidement

Cons

  • IQuestion avec des champs optionnels selon le type
  • Moins strict côté TypeScript
type IQuestion =
  IMediaQuestion
  | IOrderQuestion
  | ITextQuestion

interface IOrderQuestion {
  type: 'Order'
  orderItems: OrderItem[]
  correctOrder: string[]
}

B — Union discriminée

Chaque type de question a sa propre interface TypeScript. Le compilateur garantit que les champs sont présents selon le type. Nécessite de refactoriser les composants avec des guards (isOrderQuestion(q)).

Pros

  • 100% type-safe
  • Contrats clairs par type

Cons

  • Refacto store, gateway, composants
  • Surcharge pour le scope actuel
// Mongoose Discriminator
@Schema({ discriminatorKey: 'type' })
class Question { ... }

@Schema()
class OrderQuestion extends Question {
  orderItems: OrderItem[]
}

C — Discriminateurs Mongoose

Schemas distincts côté MongoDB via les discriminateurs Mongoose. La collection garde un seul index, mais chaque sous-type a ses propres champs validés. Cohérence parfaite entre TypeScript et MongoDB.

Pros

  • Validation DB par type
  • Architecture "correcte"

Cons

  • Complexité accrue
  • Migration des données existantes
  • Bien au-delà du scope
